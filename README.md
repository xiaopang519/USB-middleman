# RP2040 USB 中介人

**把"手"做进硬件层。**

一块 RP2040 烧成真键盘/真鼠标，插在被控机上。控制机算完坐标，通过 TCP 让板子发真实的 HID 报文 ——
被控机收到的不是"合成输入"，是键盘鼠标事件。配上采集卡"看"、图色识别"判"，就是一套眼手分离的双机自动化方案。

```
                 ┌──────────── 控制机 A ────────────┐
   HDMI ──采集卡──> ffmpeg ──> latest.png ──> 眼（图色/识别）──> 你的决策层
                                                    │
                                                    │  TCP 8300（一行命令 → 一行回执）
                                                    ▼
                                          代理 hand_agent ──HID feature report──> RP2040 ──USB──> 被控机 B
```

两条规矩，都是踩出来的：

- **决策层不碰板子**：它只会跟代理说一行话。代理是板子唯一的主人。
- **眼和手都不做判断**：判据只有一份，在决策层。否则会出现"面板说一套、执行按另一套"。

## 为什么不用软件注入

三种"软件手"的死法，都在这套机器上实测过：

| 做法 | 实测结果 |
|---|---|
| `SendInput` | 前台是管理员权限窗口时被 **UIPI 静默丢弃** —— 返回值仍报成功、`GetLastError` 仍是 0。只有"效果"能证明它到底有没有生效 |
| `SetCursorPos` | 同一台机器返回 1 且光标真的动了；另一台返回 `False`，真实原因至今未定 —— 靠不住 |
| 驱动级注入（Interception） | 要装内核驱动、要管理员权限，杀软对这类 DLL 普遍敏感 |

硬件 HID 走的是驱动栈最底层：宿主看到的就是一只真鼠标，跟它怎么筛合成输入没有关系。
这也是本项目的全部价值 —— 不是"更隐蔽的技巧"，而是**换了条物理通路**。

## 两种部署形态

| | 双机（推荐） | 单机 |
|---|---|---|
| 眼 | 采集卡接被控机 HDMI | 截本机屏幕 |
| 手 | 板子插被控机，代理走局域网 | 板子插本机，代理走 `127.0.0.1` |
| 代码 | 同一条 | 同一条（只是 `配置.json` 里地址不同） |

A/B 用同一份代码是刻意的：任何"只在本机能跑"的分支，都会在双机时变成幽灵 bug。

## 硬件

| 件 | 说明 |
|---|---|
| RP2040 板 ×2 | 本项目在 **Waveshare RP2040-PiZero** 上跑通；任意带 USB 的 RP2040 都可以（TinyUSB） |

## 快速开始

```powershell
pip install hid numpy opencv-python pillow
```

**1. 烧固件**（上面说的 uf2）

**2. 起代理**（在被控机 / 板子插着的那台上）

```powershell
python 手\代理\hand_agent.py
```

**3. 起采集**（控制机，PowerShell 里跑；帧路径按 `配置.json` 改）

```powershell
ffmpeg -hide_banner -loglevel error -f dshow -video_size 1920x1080 -framerate 10 `
       -pixel_format yuyv422 -i video="USB3 Video" `
       -f image2 -update 1 -atomic_writing 1 -y C:\Users\you\dsh_capture\latest.png
```

> 为什么强调"PowerShell 里跑"：在服务会话里由 Python 派生的 ffmpeg 拿不到 DirectShow 设备
> （`Unable to BindToObject`）。分离进程 + 用户会话里跑是可以的，但别赌这个差别 —— 手册就写一种做法。

**4. 验眼**

```powershell
python examples\01_eye_check.py
```

**5. 验手**（只读，不动机器）

```powershell
python examples\02_hand_check.py        # 或 python examples\02_hand_check.py B
```

**6. 让它真动一下，并用效果自证**

先把 `配置.json` → `安全.允许移动` 改成 `true`，然后：

```powershell
python examples\03_move_and_verify.py       # 右移 60px，读光标前后差值
```

`03` 想教的是整个项目最贵的一课：**回执 OK ≠ 事情发生了**。所以它读光标 → 发命令 → 再读光标，
差值对不上就报"没动"，绝不报成功。

## 三条铁律

1. **一块板只伺候一个客户端。** 后连上来的会把前一个 `RST` 掉（`WinError 10054`），双方都表现为"时灵时不灵"。
   所以控制端用短连接：连 → 发 → bye；没人用的板子不随手探测；**会动东西的命令绝不重试**（重试 = 动两次）。
2. **ffmpeg 只由 PowerShell 起。** 见上面那条。
3. **读不到就返回 None，绝不猜。** 帧龄超限当没看见；`status` 没回包就报红。
   面板上说的每个字都必须来自同一份判据。

## 实测台账（这套机器上的真实数字）

| 项目 | 实测 |
|---|---|
| 采集 | 1920×1080 @10 fps，帧龄 0.03–0.09 s |
| `status` 往返 | 16 ms（本机）/ 36 ms（跨机） |
| `px/count` | A 板 **2.575**，B 板 **2.49** —— 同型号个体差 3%，走 20 格就差半格，**必须逐板标定** |
| 真人让路窗 | 8 s（板子检测到真人输入后静默 8 秒，期间的命令被拒） |
| 自抑制窗 | 250 ms |

最后一条有个反直觉的坑，值得单独说：短连接关闭时如果无条件发 `release`，而 `release` 本身是一次真注入，
它的按钮事件会晚于 250 ms 自抑制窗被读到 → 被记成"真人在动" → 接下来 8 秒动作全被拒。
现场表现是"每次问一句 status 之后就走不动了"。所以：**没按下过就不发 release**。

## SDK：单机软件版（`SDK/`）

主线是硬件方案，`SDK/` 是**没有硬件时的对照实现**，也是这套方法论的完整教材：

```
perception/  感知：抓帧、找窗、找目标
decision/    决策：有状态地选目标，输出意图，不直接调执行
action/      执行：Interception 驱动级注入（软件兜底，非主线）
check/       校验：动作有没有真的发生
system/      系统层：配置、错误、急停热键
support/     支撑层：标定
```

四层 + 支撑 + 系统的分层、接口契约、逐层独立测试，都在 `SDK/接口契约.md` 和 `SDK/架构总览.md` 里。
它演示的是**契约不变、实现可换**：把 `action/` 换成 RP2040 桥，其余三层一行不用改。

> `SDK/action/` 的 Interception 路径需要你自己安装驱动（[oblitum/Interception](https://github.com/oblitum/Interception)），
> 仓库里**不附带** `interception.dll`。该驱动是双许可：非商业 LGPL v3，商业用途需向作者购买授权。

## 这个仓库**不含**什么

诚实地说明边界 —— 下面这些不是遗漏，是刻意剔除：

- **不含业务决策层**（具体做什么、什么顺序做）。框架是通用的，业务是每个使用者自己的事。
- **不含任何画面素材、截图、地图数据、识别模型权重**。仓库里能跑的例子只用你现场的帧。
- **不含操作面板**。面板和业务层绑得很紧，放进来只会得到一排按不动的按钮。

所以它是一个**方案 + 教材**，不是开箱即用的成品。你要做的是：把 `眼/` 的输出接进自己的判断，
把自己的意图交给 `手/`。
